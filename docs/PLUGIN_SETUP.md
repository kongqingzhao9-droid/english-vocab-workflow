# 使用 GitHub 和 Supabase 插件初始化

先固定用户确认的两个来源，再检查插件。这里的插件操作面向用户的新项目和新网站仓库。

## 检查安装和权限

1. 若能调用插件目录，分别搜索 GitHub 与 Supabase，读取相应条目的 `installed` 和状态。明确未安装时给出安装入口。已安装但未启用、未连接或未授权时，引导用户启用或完成授权。目录状态无法读取时，报告“无法核实安装状态”，提示在 Codex 插件页查看。
2. 用工具搜索或当前工具清单检查每个服务所需能力。安装状态与可调用工具分别检查。优先做只读探测，例如列出 Supabase 组织或项目、查看 GitHub 账号或有权访问的仓库。遇到授权提示按提示继续，不索要 token。GitHub 和 Supabase 分别判断，某一项不可用时仍可继续另一项。
3. 用户尚未安装时可等其安装，或由其选择按 SETUP.md 手动继续。已连接但某项写能力缺失时，只对该项采用对应后备步骤，并向用户说明原因。

## Supabase

1. 使用组织级项目管理能力时，请用户选定组织和新项目名称，确认区域。调用创建项目工具，按工具提示处理费用确认，检查项目已就绪。若连接仅限单项目或无法建项目，引导用户在后台创建新的专用项目，取得其项目标识并继续。
2. 用插件读取该项目的 API URL 和启用的 publishable 公钥。请用户在新项目的 Authentication → Users 创建自己的登录账号、确认邮箱并关闭公开注册，密码由本人在后台输入。若数据库读取权限允许，按用户确认的邮箱在该项目只读查找唯一已确认用户的 UID。若无法核实，才请用户提供 User UID。
3. 用 `scripts/vocab.py configure --supabase-url <URL> --public-key <公钥> --owner-id <UID>` 复用已固定的来源。运行 `prepare` 生成 `.local/setup.sql` 和 `.local/verify.sql`。确认目标项目和表清单，用迁移工具应用 setup.sql，再用 SQL 查询工具完整执行 verify.sql（含事务和回滚）。迁移工具若管理外层事务，可移除初始化脚本两段已有的顶层事务包装，把两段作为一次迁移；保留验证脚本的回滚。通过返回结果或迁移记录和查询确认执行完成。失败先核对迁移、表与策略实际状态，避免盲目重跑。仅在插件写权限不足时引导用户在 SQL Editor 执行对应脚本。
4. 运行本机 `status`、`probe`、`publish`。连接权限被拒绝时按 [同步流程](SYNC.md) 做只读检查，并继续尚未通过的验收步骤。使用真实匿名 HTTP 响应验收，数据库管理员查询成功不能替代它。DPAPI 密文仅保存在本机，数据库初始化只传上传凭证的哈希。登录密码、服务端密钥和私人词库不进入网页代码。

## GitHub

1. 使用插件核实授权账号与新仓库名称。若提供创建仓库及写入文件能力，优先由插件创建空仓库，再从 `.local/site/` 逐一读取九个白名单文件的原始内容并提交到 main。不要提交模板目录、整个工作目录、SQL、发布凭证或个人词库。文件超出插件限制时用 Git 原样推送，不能截断或改写。
2. 若插件提供 Pages 管理能力，启用 main 根目录发布并确认 URL 和部署状态。若缺少创建、推送或 Pages 能力，沿用 SETUP.md 的对应步骤。若已由插件创建空仓库，先记录该次创建返回的账号和仓库，使用它的明确目标继续，切勿为绕过脚本的既有仓库保护而假造本机标记或改用其他仓库。可以在该仓库用 Git 单独推送白名单，缺少 Pages 权限时引导用户在该仓库后台启用。
3. 核对远端提交文件清单与本机白名单。发布后执行现有手机登录验收。插件权限、网络、部署或登录尚未通过时，说明卡在哪一步及如何续跑。
